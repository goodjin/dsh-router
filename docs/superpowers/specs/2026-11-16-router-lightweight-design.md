# Router 轻量团队协作设计

日期：2026-11-16。状态：对话架构及本书面规格均已由用户确认（书面确认时间10:56，Asia/Shanghai）。仅设计，不代表实施或上线完成。

## 1. 目标与取代范围

Router 是 DSH 上由模型主导的团队协作插件：Router 接任务，主管组队，成员执行；模型判断下一步，用户决定最终交付是否满足要求。

本设计取代此前 Router 团队化升级方案中与之冲突的架构和 T01–T15 执行路线。不兼容、接管或导入旧插件会话；不继续旧迁移、可靠消息箱和业务权限引擎的补修。旧代码、候选分支及用户数据保留，不以本设计授权删除。

产品身份仍是 Router，沿用现有包名；“当新插件设计”不要求另改包名或同时安装两份。实现从正常主干建立隔离分支，不合入旧未验收候选。仅复用符合本设计的独立组件，不为复用保留旧控制逻辑。

## 2. 基本原则

1. DSH 管会话、通信、执行工具、持久化及宿主权限；Router 不建设第二套运行系统。
2. 模型决定拆分、派发、组队、补做、继续与汇总；插件不自动裁决业务。
3. 角色通过提示词和任务说明明确，不创建跨成员、跨任务的业务授权体系。
4. 工作记录是共享资料，不是驱动程序执行的状态机。
5. 工具如实返回保存、发送、创建失败；不把失败伪装成成功，不自动补偿。
6. 仅为实际功能建立检查：格式、目录约束、写入完整性和宿主能力支持。不引入假想的恶意同进程防御。

## 3. 角色与通信

| 角色 | 决策与工作 | 报告对象 |
|---|---|---|
| Router | 理解需求、创建任务说明、选主管、协调多个任务、汇总交付 | 用户 |
| 主管 | 拆解负责的任务、选择成员、分工、阅读结果、决定补做或汇总 | Router |
| 成员 | 执行分配工作、自检、保存报告、说明成果和未完成事项 | 主管 |

主通信结构为用户↔Router↔主管↔成员。跨成员由主管转达，跨团队由 Router 协调；第一版不建立任意成员互通网络。不强制每项工作安排独立审查者，是否审查由模型按任务决定。

创建、查询、发送消息、继续和停止直接使用 DSH 已有能力。后台子任务使用宿主的父级回传；报告完成后允许宿主正常结束该轮次。成员可主动发送进度，但不重复建设自有消息通道。

选择支持本地可继续子会话及两层派发的宿主组合；按宿主绝对深度配置 Router→主管→成员。外部一次性后端不支持后续消息时如实呈现，不冒充可继续。模型依据宿主能力选择继续原会话或新建会话，插件不另设成员复用和后台排空协议。

## 4. 单一入口与角色模板

仅提供一个用户可选 Router preset。共同的完整协作提示词使用 `complete: true`，包含三种角色职责、记录约定和报告要求；保留宿主项目指令、正常工具与默认压缩能力，不复制其内部实现。

子会话继承相同基础组合。每次创建的初始任务消息明确：当前角色、上级、任务目标、材料位置、记录目录、报告位置和专业职责；无角色指定的新根会话按 Router 工作。角色身份不要求修改系统提示词，也不声称是安全边界。

专业角色模板仅为数据：一个角色一个 md 文件（文件名=角色名、正文=职责说明），用户和模型均通过同一保存能力按名 upsert，也可以用任何编辑器直接改文件；首次启用幂等种入预置角色（v2 起共 16 个：主管/执行者/调研员/评审员 4 既有 + Python程序员/Java程序员/前端程序员/架构设计工程师/测试工程师/部署运维工程师/文档资料归档工程师/需求与PRD工程师/PRD审核员/MR审核员/代码评审员/交互设计师 12 新增），职责文案为「首行摘要 + 详细正文」两层结构——协作上下文的角色清单只注入首行摘要（控制每会话注入体积），全文只在派发时拼进被选中角色的初始指令；种入带历史文本精确升级（现有内容与某版历史预置文本完全一致才覆盖到最新，用户改过的永不动），旧 JSON 版自动迁移为 md。模板不注册 preset，不包含角色专属运行时插件树。派发经专用工具 `router_dispatch`（2026-11-18 起）完成职责注入：模型只传角色名、任务、派发方式（spawn 轻装 / fork 带父级已完成轮次），插件代码读取角色 md、把职责说明连同任务与根会话拼成子会话初始指令、经宿主 subagents 服务创建子会话并自动登记分工记录（关联 childId、待处理标签）——职责与根会话的注入是机制保证，不依赖模型自觉；原生 spawn 工具不挂入 Router 预设，防绕过。模型选择沿用 DSH 支持的配置能力，不在本插件新增模型路由器。

## 5. 模块边界

| 模块 | 保留职责 | 禁止承担的职责 |
|---|---|---|
| 入口和规则 | 装配一个 preset、统一协作提示词和记录工具 | 自动调度、自动切换角色 preset |
| 工作记录 | 任务、分工、报告、角色模板的读写及会话关联 | 推断成功、派发执行、业务验收 |
| 工作台 | 列表、详情、报告、成果链接、会话跳转、模板编辑 | 独立调度器或验收状态机 |
| DSH 接入 | 使用现有子会话工具；只读获取宿主可提供的运行事实 | 私有宿主状态读取、自有消息重放或后台回收 |

第一版不新增执行代理、SQLite 业务库、消息箱、预算熔断、任务图调度或自动修复服务。

## 6. 工作记录与存储

使用现有插件数据根下的新命名空间 `collaboration/`，不扫描旧账本。每个 Router 根会话有独立目录，每项任务有独立目录；角色模板另存于 `collaboration/roles/`。实际目录位置由插件生成并在工具响应中返回，模型无需猜测路径。

一个记录对应一个独立 JSON 文件，内容包括少量元数据和 Markdown 正文；无需同时维护可漂移的 JSON 事实库与 Markdown 副本。通过展示和读取工具直接取得 Markdown 正文，不维护第二份全局任务状态索引。

记录字段：记录编号、种类、根会话编号、可选上级记录编号、标题、正文、可选工作标签、会话关联和成果引用、创建/更新时间。编号和时间由保存工具生成；正文、标签、关联说明由模型或用户填写，不认证其业务真实性。工作标签只使用“待处理、进行中、受阻、已报告”，不设计“系统验收成功”。

| 种类 | 内容与维护约定 |
|---|---|
| 任务说明 | Router 写目标、范围、约束、交付要求、材料 |
| 分工记录 | 主管写各项工作、成员、对应子会话 |
| 工作报告 | 每个成员写自己的成果、证据、自检和未完成项 |
| 汇总报告 | 主管、Router 分别写汇总与交付说明 |

这些维护者是协作规则，不是写入权限矩阵。成员各写自己的报告，避免共享文件争抢；插件内写入串行化并原子替换单个文件，首版不支持多个宿主同时写同一份记录目录。显式修改同一记录按提交顺序保存，不引入工作流锁、执行令牌或多文件事务。

工具仅按生成的编号在受控数据根内保存，不允许任意写入路径或目录越界；成果路径是展示引用，不自动读取、执行或覆盖目标。用户直接手改记录文件不属于工具的并发一致性保证。损坏或缺失返回明确错误，不自动创建空记录冒充原记录。

## 7. 工具与调用顺序

只新增两类工具能力：
- 工作记录：创建、读取、列表、更新；响应含记录编号、位置及保存结果。可指定本次任务资料目录，不推断任意旧会话归属。
- 角色模板：列表、读取、保存。保存模板没有创建会话或派发任务的副作用。

具体工具名在实施计划固定，不为 CRUD 方法再建立通用命令总线。新根目录建立后，Router 在向主管派发时传递记录位置，主管向成员继续传递；目录和身份说明来自任务上下文，不要求插件维护另一份执行归属数据库。

正常流程：Router 保存任务→用 DSH 创建主管→记录返回的子会话关联→主管保存分工并创建成员→成员保存报告→用 DSH 向主管报告→主管判断并汇总→Router 向用户交付。

保存和通知是两个独立动作，不承诺原子性或恰好一次。报告保存成功但通知失败时，文件仍保留，模型根据错误决定重发链接或说明阻塞；不自动重跑工作。重复通知可引用同一记录，由模型理解。创建成功但关联保存失败时，保留并告知宿主返回的会话编号，模型补记，而非程序另建一个成员。

## 8. 展示、异常与恢复

工作台是会话标签行（`conversation.view`）的「协作」视图页，整页显示在会话界面里（2026-11-18 起取代旧「头部按钮 + 弹出卡片」形态，挂法与官方统计页同款）。页头为根会话选择（留空默认当前会话）与刷新；其下是两个标签：**任务**与**角色**。任务标签：任务画布（节点=任务卡：标题与四态进度 待处理/进行中/受阻/已报告；连线=派生关系，由会话父子推导——任务 A 的成员派出的会话若是任务 B 的成员则连 A→B，无派生来源的任务挂虚拟根成林）+ 任务详情（任务说明、会话画布、分工列表、报告列表、选中记录详情）。会话画布以节点卡片展示该任务的成员会话（角色名、实时运行状态、能对上分工的工作标签），连线为 subagentCatalog 给出的真实父子关系。角色标签：左侧角色列表（含「新建角色」草稿项）、右侧查看/编辑（名称 + 职责多行编辑框，**保存才生效**，未保存有标记；与模型共享同一 RoleStore，按名 upsert）。会话/任务画布数据来自页面会话标准属性，按需经 sessions.refreshProjections 加载，不新增后端。

工作台将三类信息分开：DSH 的运行事实、模型报告的工作描述、用户反馈。运行完成不改写业务标签；测试通过不自动表示交付合格；子会话状态不可取得则显示未知，不推断为失败或成功。任务与团队跟着记录走：无任务说明记录的任务卡标题退化为任务编号；无关联会话的任务保留整棵子会话树；记录关联但不在树内的会话列为孤儿，不臆造父边。

工作台提供记录浏览、正文、成果引用、会话跳转及角色模板编辑。第一版不新增自动验收按钮或自有停止/恢复后端；用户通过聊天提出处理要求，模型调用 DSH，必要时进入宿主会话界面处理。

创建或消息失败由 DSH 返回；保存失败由记录工具返回。模型决定补充、重试、换人或终止，插件不自动重派。停止遵从宿主能力，不能承诺撤销已产生的外部影响。宿主恢复新插件会话后，模型重新读取任务记录和宿主状态；不添加插件启动时自动续跑逻辑。

## 9. 必要改造与明确排除

改造范围仅为入口/提示词、轻量记录工具、角色模板与工作台数据接入。旧控制模块不再挂入新入口；具体代码删除前核对引用，只在隔离分支处理，不删除已有用户数据。既有 UI 展示组件、文件 IO、日志、打包设施可复用，但不得引入旧任务控制服务。

不纳入：旧会话迁移、历史归档许可、旧数据库升级/回退、业务授权引擎、独立投递状态机、自动成功判断、自动补做、自动更换执行者、跨任务异步资源排空、第三方恶意插件隔离。新需求不得借“健壮性”名义自动加入这些机制。

## 10. 验收与实现边界

1. 用户只需一个 Router 入口；主管和成员不额外出现在 preset 列表。
2. 本地真实 DSH 场景可完成 Router 创建主管、主管创建成员、成员回报主管、主管回报 Router；没有启动第二套通信系统。
3. 子会话实际收到正确的职责、任务说明和记录位置；手动及模型创建的模板均可用于派发，不注册新 preset。
4. 记录 CRUD、串行/原子保存、目录约束和错误返回有效；模型报告不会因通知失败被删除。
5. 工作台正确区分宿主状态与模型结论；没有后台自动验收、补做、换人和恢复派发。
6. 会话无法继续、发送失败、记录保存失败均向模型说明；不使用伪成功、静默降级或无界重试。
7. 仓库类型检查、测试、构建通过且产物一致；修改声明行须在候选组合核对 CLI/桌面两版宿主，修改客户端须做候选客户端激活检查。
8. 实际任务演练只证明协作路径可用，不宣称系统可以自动判断任意工作质量；最终成果由用户评价。

只测试本设计实际支持的机制，不继承旧方案庞大故障矩阵。代码实施、真实部署、推送或重启仍需对应阶段授权；本设计提交不改运行中的插件。
