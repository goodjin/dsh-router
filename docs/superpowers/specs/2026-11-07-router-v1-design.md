# dsh-router v1 设计规格（已批准）

> 本文档是 2026-11-07 与用户逐轮确认后批准的实施规格。实施计划见
> `docs/superpowers/plans/2026-11-07-router-v1.md`，计划从本文档出发生成，
> 两份一起阅读。冲突时以本文档为准；本文档未尽处由计划定死并注明。

## 1. 背景与目标

一个长期在线的任务编排插件：用户始终与 Router 会话交流，Router 理解需求、澄清、
整理任务并派发；真正的工作由独立的 worker 会话完成。即使多个 worker 正在执行或
等待用户回答，Router 仍能继续接收新需求。

插件名 `@goodjin2/dsh-router`，独立仓库，不依赖本容器其他插件。

## 2. 对象模型

| 对象 | 职责 | 生命周期 |
|---|---|---|
| Router 会话 | 与用户交流、整理任务、派发、汇报状态 | 长期存在 |
| 任务 | 目标、约束、验收、状态、关联会话 | 从提出到完成，完成后归档 |
| Worker 会话 | 接受任务、执行、提问、交付 | 独立持久会话，左侧常驻，可再打开 |

- **角色**（权限维度）：`router` / `supervisor`（主管型） / `worker`（工作型）。
- **专业类型**（配置维度）：编码、调研、文档、测试、审查……即 worker 模板。
- 主管型可继续派发子任务（含再派主管，受最大深度限制）；工作型不可派发。
- **父子关系**（谁负责）与**依赖关系**（开始前需哪些交付物）严格分开。
- 默认一个任务一个 worker 会话；同任务补充/返工投递给原 worker。
- Worker 停止生成 ≠ 任务完成；完成必须走 `complete_task` 工具协议。

## 3. 入口与界面

### 3.1 创建入口

项目栏每个项目旁增加「＋」入口，菜单含「新建 Router」。创建时绑定当前项目工作
目录、选择 Router 模板（可改名/模型/提示词）、创建普通持久会话（左侧 Router
图标区分）、默认打开 Router 视图。一个项目可有多个 Router，共享项目记忆、各自
管理任务树。若宿主无左侧注入点，退而求其次：hero/会话头部入口或命令入口，实现
时按查证结果定死并记录。

### 3.2 两层导航（与 chat-power 共存）

```text
第一层（本插件）：会话导航标签条——切换 Router/worker 会话
第二层（chat-power）：当前会话内工具标签（会话/文件/终端…）
```

规则：
- 新派发任务不抢焦点，默认保持 Router 为当前标签。
- 关闭 worker 标签只关视图，不停止任务、不删左侧会话；左侧点击可重开标签。
- 完成任务保留会话与结果；标签可手动关闭。
- 职责边界：会话导航/任务树/问题汇聚归本插件；会话内文件/终端/浏览器/编辑标签归
  chat-power；原生右侧栏归宿主。不安装 chat-power 时本插件独立可用。
- 不直接操作 chat-power 内部状态；单条标签栏合并属后续兼容改造，不在 v1。

### 3.3 问题浮窗（Router 界面内）

- worker（含主管）向用户提问 → 汇聚到 Router 界面浮动卡片区，默认收起，显示
  任务名与问题摘要；点击展开，支持单选/多选/自由文本。
- 提交后显示「正在送达」，服务端确认接收后自动消失；失败保留卡片与已填内容。
- 收起不是回答；多个 worker 的问题分别排队互不覆盖。
- 回答由插件直接送达对应 worker，不经 Router 模型转述；Router 只收状态更新。

## 4. Router 上下文：任务账本 + 工作摘要

- **可查历史**完整保留（会话日志）；**发给模型的上下文**只含调度所需。
- Router 每轮实际可见 = 角色提示词 + 精简长期记忆 + 当前未派发需求 +
  全部未结束任务短卡（活动账本快照）+ 本轮用户消息 + 未处理必要通知。
- 活动任务短卡字段：任务 ID/标题、目标与关键验收、worker 类型/会话 ID、状态/
  一句话进度、依赖、待回答事项、最新补充约束。
- **每次成功转交后执行一次上下文整理**：存完整任务书 → 确认入箱 → 压缩相关讨论
  为短摘要 → 替换模型历史对应内容 → 后续状态更新覆盖卡片（不追加重复摘要）。
  摘要失败保留原上下文重试，禁止重复派发。
- 一条消息多需求：已派发部分可压缩，仍在澄清部分必须保留。
- **完成任务**：存结果与交付记录 → 完成卡片 → 从下一轮活动上下文移除 → 交付物
  引用转移给后续任务 → 归档可检索。旧任务摘要必须同步退出模型历史。
- 未结束任务全保留（排队/执行/等待用户/暂停/失败待处理）；任务多时缩短卡片，
  不静默丢弃；活动容量可配置，防撑爆窗口。

## 5. 任务文档协议（派发即文档）

每个任务稳定 ID，目录 `tasks/<ID>/`：

```text
task.v1.md   原始任务书（不可变）
task.v2.md   补充要求后的新版本
progress.md  当前进展摘要（执行者更新）
result.md    最终交付报告（完成时生成）
```

任务书字段：目标/背景/范围、约束、验收条件、所属项目与工作目录、指派角色与专业
类型、父任务与依赖任务、输入材料与交付物引用、来源会话与消息引用、文档版本。

派发流程：形成任务书 → 持久化版本 → 校验依赖与权限 → 投递文档引用+版本 →
worker 接收（初始输入含任务书全文，不只给路径）。主管向下派发遵守同一协议；
从最终结果可一路追溯到最初需求。文档管阅读/回溯/共享；运行状态/投递去重/依赖
解锁由持久任务账本管（按 taskId+版本关联）。

## 6. 记忆：所有会话的文档化记忆

- **会话摘要**（每会话一份，增量更新）：需求、决定、结果、未决事项、来源引用。
- **项目记忆**：项目约定、已确认事实、重要交付物（当前项目优先检索）。
- **全局记忆**：明确长期偏好、跨项目约定（精简后常驻或按需读）。
- Router 常驻上下文只含：角色提示词 + 精简长期记忆 + 未派发需求 + 活动任务短卡
  + 本轮相关记忆片段。
- 规则：结论带来源会话与消息范围；用户决定/worker 建议/已验证事实分别标记；
  冲突保留冲突不合成；记录摘要已处理到的事件位；低信息内容不入记忆；历史会话
  后台补建不阻塞接单。完成任务移出活动上下文但结果进记忆。

## 7. 完成协议：`complete_task` 工具

提交字段：任务 ID、执行版本、结果摘要、结果文档引用、交付物引用、验收依据、
遗留问题。

服务端校验：调用者是当前任务执行者；针对当前有效执行版本（旧 worker 迟到提交
拒绝）；必填完整；主管任务无未结束必需子任务；重复提交幂等去重。

**调用工具 = 申请交付；是否完成由验收策略定**：`auto`（校验过即完成）/
`supervisor`（主管验收后完成）/ `user`（Router 出验收卡，确认后完成）。

失败或阻塞用独立状态工具（`report_blocker`），不得用完成工具掩盖。模型自然结束、
空闲、关标签都不算完成。完成被接受后由服务端统一执行：存结果、记忆更新、通知
上级、解锁依赖、清理活动上下文——Router 不在生成也能推进。

## 8. 调度可靠性规则

- 派发幂等；持久化（重启恢复任务关系、待答问题、会话入口）。
- 完成有协议（见 §7）；中断不伪装成功（标中断/待恢复）。
- 并发受控（按 worker 类型上限排队），Router 不等待 worker。
- 修同一仓库的 worker 用独立 worktree 或串行；取消精确定位到任务。
- 关视图/刷新浏览器不影响执行；上下文整理期间新消息入队不丢。
- 主管递归派发受最大深度、并发、任务数限制；拒绝循环依赖。

## 9. v1 范围

做：上述全部（入口按查证结果取最优挂点）、任务/记忆文档持久化、worker 会话桥、
问题浮窗、完成协议、依赖解锁、活动账本上下文 + 派发后压缩、模板与提示词配置
（配置文件形态）、重启恢复。
不做（记录为后续）：模板可视化编辑器、导出分享打包、多 Router 协同、web profile
安装验证、chat-power 单条标签栏合并、记忆向量检索。

## 10. 验收标准

1. 连续提出多个需求，Router 持续分派不阻塞、不抢焦点。
2. 关闭 worker 标签/刷新页面不影响执行；重启后任务关系与待答问题恢复。
3. worker 提问集中浮现在 Router 界面；回答后消失并继续执行。
4. 任务完成后：左侧会话仍在、活动上下文移除、记忆与 result.md 可检索。
5. 主管型能派发子任务并按依赖启动；工作型无派发工具（执行时校验）。
6. 门禁：typecheck / test / build 全绿；装载接线测试过；容器核查双宿主绿。
