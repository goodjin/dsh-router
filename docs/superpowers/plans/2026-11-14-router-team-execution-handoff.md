## 2. 开发团队组织

采用一个执行Lead和扁平的专业成员；不要让每位开发成员再自行建立未受控子团队。成员数量按当前工具上限分批，不要求同时创建全部角色。

| 成员职责 | 主任务 | 允许写范围 | 必须交付 |
|---|---|---|---|
| 契约/存储 | T01–T03 | shared/v2、store、契约测试、probe | 宿主能力证据、事务与幂等反例、冻结接口 |
| 协议 | T04、T08 | domain、application/tasks/graphs/results/teams/dispatch、对应测试 | 任务/图/成员/主动报告与验收正确性 |
| 角色/权限 | T05–T06 | roles、scope-installer/prompt-composer/tool-guard/mode-binding、对应测试 | 手建/自动角色、唯一complete、越权反例 |
| 宿主运行 | T07、T09 | dsh-adapter/host-port/dispatch/recovery/outbox/mailbox/waiter/documents、对应测试 | 首步身份与崩溃恢复实证、消息可靠性 |
| 健壮性 | T10 | safety、对应测试 | 停止/迟到结果、熔断、范围/预算、异步清理 |
| 视图/界面 | T11–T12 | presentation、client/v2、对应测试 | 读模型/Session投影、工具API、UI与激活证据 |

这是责任划分，不是允许抢改重叠路径。T01–T03先由一位基础负责人完成，Lead审阅冻结接口后再分发下游。application/service、shared/types和HostPort的公共变更必须由Lead协调；所有者之间先给接口变更提案，不先改后通知。

## 3. 分批执行顺序

### Wave 0：证据和基线

Lead：确认用户已批准方案，开执行worktree，记录git状态；跑基线三门禁；建立共享任务板；先发T01。真实宿主能力缺失时停依赖任务，明确替代方案需重新批准，不让成员自行绕过。

### Wave 1：纯内核

T02→T03；之后T04与T05可以独立推进。到这里不改用户正在运行的装配，不启用真实派发。评审重点是事务回滚、读取对象权限、失败节点不能success。

### Wave 2：身份与会话

T06→T07；T08接成员模型，T09接消息/文档。第一次真实模型验收只做一个主管和一个worker，不直接压力并发。通过首步身份、冷恢复后才扩大团队。

### Wave 3：停止、防护和视图

T10与T11在依赖满足后并行，T12组装工具/API/界面。每个模块仍写自己的范围；旧UI入口接线由集成人员收口。

### Wave 4：兼容与总装

T13可以在契约稳定后提前做只读迁移测试；T14在前述能力通过后合入集成分支。所有新旧运行所有权明确后，才开启独立profile的v2 flag。

### Wave 5：独立验收与交付

T15按设计A–J跑全矩阵，review员不能仅复述实现者的报告。Lead等待必需成员与评审全部结论后才能给最终完成答复。未验证项标blocked/untested，不能写成已通过。

## 4. 工具与任务板使用约定

- 派发工具必须遵守执行会话当前的系统/开发者工具约束；若预设要求通过`delegate_skill`分派，不绕到禁用的plain subagent或其他入口。若启用官方Team工具且允许创建成员，可用spawn_teammate建立本开发团队，任一模式都不得绕过用户设定的模型路由。
- 每个任务写明T编号、commit基线、依赖、接口、writeScopes、验收与禁止操作。共享任务板的writeScopes只是提示，不是文件锁；真正隔离靠独立git worktree和集成所有权。
- 领取前list/get，带当前revision claim；完成前提交完整报告与证据，再complete。发生CAS冲突先重新读，不盲重试相同revision。
- 消息目标使用工具返回的可寻址标识。已发送不代表已处理，inactive不代表任务完成。
- 等待前确认必需成员running/provisioning；无可进展成员不要循环wait，先查任务和最后报告，需要继续再发消息。
- 每位成员独立分支与worktree，只提交自身变更。不得同时在共享主工作区运行格式化/生成/构建写入。
- 发生宿主/存储/安全契约阻断时立即报告Lead，不能换名字重派、增加预算或更换接口掩盖问题。

## 5. 每项交付的报告格式

报告必须由工作会话主动提交，不用idle代替交付。当前工具没有产品级报告工具时，用团队消息及共享任务板提交同等内容；待升级后应由Router结果协议承载。

必填：

- task：T编号、目标、分支、base commit、交付commit。
- scope：修改范围、是否触碰共享入口、是否新增宿主依赖。
- contracts：消费/产出的接口名与变化；未改也明确写“无”。
- tests：红灯命令和失败原因、绿灯命令和exit code、测试数量、真实宿主版本/模型/证据位置。
- result：完成内容、报告/产物引用、仍未完成项、已知风险；禁止仅写“实现好了”。
- recovery：本任务涉及哪些崩溃/停止/重试窗口、实际验证了哪些。
- review：独立review结论、问题列表、修复commit和复跑证据。
- handoff：下游需要的接口与初始化步骤、阻塞条件、后续建议。

产品中的跨角色任务交接还应携带task/revision/run/attempt、roleVersion/promptHash、stopEpoch、已接受结果与证据、未决问题和writeScopes；旧attempt报告必须按版本/epoch拒绝结算。

## 6. 审查与合并规则

每项先规格审查（有没有做对需求）再代码/可靠性审查。审查重点至少包括：

1. 没有用完整提示词替代程序权限；身份不是从模型文本读取。
2. 没有把宿主接受消息当模型处理完；没有发送前标delivered/consumed。
3. 没有在创建后才登记唯一身份；异常重试不新建另一childId。
4. 没有两个账本/定时器同时驱动同一任务。
5. 没有“全部已结束”就算成功、没有忽略failure或旧验收。
6. 没有把数据库查询塞进Session投影fold；投影不是第二真源。
7. 没有未收集的UI测试、没有只核主仓却声称候选通过。
8. 没有裸void异步异常、失效ctx访问和静默降级成功。

集成人员按依赖顺序cherry-pick经过审查的提交；每次合入跑相邻模块回归。所有共享产物最后统一构建，成员不得各交一份互相覆盖的lib/client.js。合主干前typecheck/test/build+宿主行+client激活+独立web实测全绿；用户桌面重启单独确认。

## 7. 交付与授权边界

- 可以自动启停自己创建的临时web实例，不得kill/quit/restart现有桌面。
- 不修改Kernel源码/当前数据，不移除它的profile引用；若最终要下线Kernel，先单独盘点使用方、数据与会话，再请用户确认。
- 不删除旧preset、旧任务文档或用户文件来“清理测试”；测试只用带隔离标识的临时目录，删除前核对绝对路径。
- 不自动扩大任务到模型适配、宿主升级、其他插件重构。真实能力不足作为阻断提交，不借修改宿主解决。
- 推送远程、正式profile切换与桌面重启遵守用户当前授权与仓库发布流程；有风险的生产数据迁移先给dry-run和备份报告。

最终用户报告必须分别写：代码完成、自动测试、真实宿主验证、数据迁移、部署生效五项状态。任何一项未做不得用一个“完成”覆盖。
