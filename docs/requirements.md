# dsh-router 需求规格（轻量协作版，唯一需求权威）

日期：2026-11-16。状态：轻量协作设计已由用户确认（`docs/superpowers/specs/2026-11-16-router-lightweight-design.md`）。
本文件以该设计为唯一权威，描述当前架构；历史上的 executor/dynamic/aliases/三层记忆/状态机/
收编/worker 类型等旧方案见 `docs/superpowers/specs/` 与 `docs/superpowers/plans/` 的历史记录，
**旧方案与本文件冲突处一律以本文件为准；旧用户数据与历史分支保留、不删、不兼容、不迁移**。

## §1 目标与定位

Router 是 DSH 上**由模型主导**的团队协作插件：Router 主会话直接担任主管——接任务、组队、派发、
跟进、汇审；成员执行；模型判断下一步，用户决定最终交付是否满足要求。（两级模型，2026-11-24 起；
设计见 `docs/superpowers/specs/2026-11-24-router-two-level-supervisor-design.md`。）DSH 管会话、通信、执行工具、持久化及宿主权限；插件只
保存资料、提供规则、展示事实。插件不建设第二套运行系统。

## §2 角色与通信

| 角色 | 决策与工作 | 报告对象 |
| --- | --- | --- |
| Router | 拷问式对齐理解需求、建任务、自己组队与分工、阅读结果、决定补做或汇总交付 | 用户 |
| 成员 | 执行分配工作、自检、保存报告、说明成果和未完成事项 | Router |

主通信结构为用户 ↔ Router ↔ 成员。跨成员由 Router 转达，跨团队由 Router 协调；第一版不建
立任意成员互通网络。角色通过提示词与任务说明明确，不创建跨成员、跨任务的业务授权体系，不声称
是安全边界。

## §3 单一入口与角色模板

用户只需一个 Router 入口（`dsh-router` / `Router`）。成员不额外出现在 preset 列表，继承
同一基础组合。共同协作提示词 `complete:true`，包含两种角色职责（Router 直接担任主管，含原主管的
组织纪律）、记录约定和报告要求；保留宿主
项目指令、正常工具与默认压缩能力。每次创建的初始任务消息明确：上级、任务目标、材料
位置、记录目录和报告位置；**专业职责不进任务消息**——它由协作上下文按会话注入子会话的
系统提示词（归属从分工记录反查），无角色指定的新根会话按 Router 工作。

专业角色模板仅为数据：模板编号（稳定 ID，=md 文件名）、名称、职责说明。用户和模型均通过同一保存能力
创建/修改（带 ID 按 ID 更新、不带 ID 新建；名称全局唯一，改名只改文件内容、文件路径不动）；派发时
只传角色名，职责说明由代码注入子会话的系统提示词。模板不注册 preset，不包含角色专属运行时插件树。

## §4 工作记录与存储

新数据使用插件数据根下的 `collaboration/` 命名空间，不扫描旧账本。每个 Router 根会话有独立目录，
每项任务有独立目录；角色模板另存于 `collaboration/roles/`。一个记录对应一个独立 JSON 文件，含
少量元数据和 Markdown 正文；不同步维护可漂移的 JSON 事实库与 Markdown 副本。

记录字段：记录编号、种类、根会话编号、可选上级记录编号、标题、正文、可选工作标签、会话关联、
成果引用、创建/更新时间。编号和时间由保存工具生成；正文、标签、关联说明由模型或用户填写，不
认证其业务真实性。工作标签只用「待处理、进行中、受阻、已报告」，**不设计「系统验收成功」**。

| 种类 | 内容与维护约定 |
| --- | --- |
| 任务说明 | Router 写目标、范围、约束、交付要求、材料 |
| 分工记录 | Router 派发时自动登记：成员、对应子会话；`sessions` 是追加需求时的投递目标 |
| 工作报告 | 每个成员写自己的成果、证据、自检和未完成项 |
| 汇总报告 | Router 写汇总与交付说明 |

插件内写入串行化并原子替换单个文件；显式修改同一记录按提交顺序保存，不引入工作流锁、执行令牌、
多文件事务。工具仅按生成的编号在受控数据根内保存，不允许任意写入路径或目录越界；成果路径是展示
引用，不自动读取、执行或覆盖目标。损坏或缺失返回明确错误，不自动创建空记录冒充原记录。

## §5 工具与调用顺序

只新增两类工具能力：工作记录（创建/读取/列表/更新，响应含记录编号、位置及保存结果）与角色模板
（列表/读取/保存）。工具如实返回保存、创建、失败；不把失败伪装成成功，不自动补偿。

正常流程：Router 拷问式对齐 → 保存主任务 → `router_dispatch` 按角色派发成员（每次派发可新建
任务并把子会话挂上去；分工记录自动登记）→ 成员保存报告 → 用 DSH 向 Router 报告 → Router 判断并
汇总 → 向用户交付。Router 用 `router_compact` 把上次压缩以来的对话压成任务列表检查点；活跃任务的完整描述每步注入上下文。

保存和通知是两个独立动作，不承诺原子性或恰好一次。报告保存成功但通知失败时，文件仍保留，模型
根据错误决定重发链接或说明阻塞；创建成功但关联保存失败时，保留并告知宿主返回的会话编号，模型
补记，而非程序另建一个成员。

## §6 工作台（只展示事实）

工作台将三类信息分开：DSH 的运行事实、模型报告的工作描述、用户反馈。记录浏览、正文、成果引用、
会话跳转及角色模板编辑；首版工作台**只读任务资料**（记录修改由工具负责）。运行完成不改写业务
标签；测试通过不自动表示交付合格；子会话状态不可取得则显示未知，不推断为失败或成功。保存错误
不返回 200，显示具体错误及重试，不伪装成空列表。首版不新增自动验收按钮或自有停止/恢复后端。

## §7 必要改造与明确排除

改造范围仅为入口/提示词、轻量记录工具、角色模板与工作台数据接入。旧控制模块不再挂入新入口；
具体代码删除前核对引用，只在隔离分支处理，不删除已有用户数据。既有 UI 展示组件、文件 IO、日志、
打包设施可复用，但不得引入旧任务控制服务。

不纳入：旧会话迁移、历史归档许可、旧数据库升级/回退、业务授权引擎、独立投递状态机、自动成功判断、
自动补做、自动更换执行者、跨任务异步资源排空、第三方恶意插件隔离。

## §8 验证与实现边界

1. 用户只需一个 Router 入口；成员不额外出现在 preset 列表；「主管」角色已退役，不可派发。
2. 本地真实 DSH 场景可完成 Router 创建成员、成员回报 Router；没有启动第二套通信系统。
3. 子会话实际收到正确的职责、任务说明和记录位置；手动及模型创建的模板均可用于派发，不注册新 preset。
4. 记录 CRUD、串行/原子保存、目录约束和错误返回有效；模型报告不会因通知失败被删除。
5. 工作台正确区分宿主状态与模型结论；没有后台自动验收、补做、换人和恢复派发。
6. 会话无法继续、发送失败、记录保存失败均向模型说明；不使用伪成功、静默降级或无界重试。
7. 仓库类型检查、测试、构建通过且产物一致；修改声明行须在候选组合核对 CLI/桌面两版宿主，修改
   客户端须做候选客户端激活检查。
8. 实际任务演练只证明协作路径可用，不宣称系统可以自动判断任意工作质量；最终成果由用户评价。

仓库三门禁（`npm run typecheck` / `npm test` / `npm run build`）全绿、入库产物一致、候选绝对路径
双宿主声明核查与客户端激活核查通过，才算完成。代码实施、真实部署、推送或重启仍需对应阶段授权；
本设计提交不改运行中的插件。

## §9 旧方案退役说明

本设计取代此前 Router 团队化升级方案中与之冲突的架构与执行路线。旧代码、候选分支及用户数据保留，
不以本设计授权删除；新数据用 `collaboration/` 命名空间，与旧数据不兼容，不扫描、导入、接管旧会话
或旧账本。退役的旧功能模块与其替代验证见
`docs/superpowers/reports/2026-11-16-router-lightweight-verification.md` 的退役映射表。

### 派发建任务与追加需求

`router_dispatch` 的 `taskId` 可选：给了就在该任务下派发（一个任务可挂多个子会话）；省略则自动新建一条任务（`taskTitle` 必填；`parentTaskId` 可选，新任务挂父任务下，通常传主任务）。对同一交付物的追加或修改，先用 `router_record_list(taskId, kind=assignment)` 查出该任务下登记的子会话，再用 `mode=continue` 并提供 `expectedChildId` 投递——continue 把追加要求自动拼进归属任务的描述，再向该子会话发消息；归属必须唯一，零个或多个都拒绝、不猜；无回执时报失败，不换用新建模式或 Team 消息。

### 压缩工具与任务描述驱动的上下文

不自动压缩。给主会话一个 `router_compact` 工具，行为规则引导何时压（一个任务收到报告处理完之后、连续几轮讨论落定之后、历史很长还不想结束时；一个任务压一次）。它只压**上一次压缩以来**的已闭合回合（当前轮一个字不动，工具调用/结果不切开），把那段对话原位取代成一份**任务列表检查点**：从工作记录生成（每条任务的状态、一句目标、子会话、最近报告，子任务挂父任务下）+ 模型用 `notes` 附的关键决策；不花一次模型调用。压之前先把关键决策写进任务描述——检查点的来源是记录。`compacted:false` 表示没有可压内容，不是错误。宿主自己的压力压缩仍作为溢出安全网存在。

协作上下文段每步注入活跃任务（未「已报告」）的完整描述与子会话，写后零滞后刷新——任务描述是「现在要做什么」的权威来源，关键决策写进任务描述而不是只留在对话里。
